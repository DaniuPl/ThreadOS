# Security

ThreadOS is a hobby operating system. It has not been audited, and it
should not hold anything you could not afford to lose. Still, some of it
exists precisely to keep things out - privilege levels, page
protections, certificate checking, signed updates - and a hole in any of
that is a bug worth reporting.

## Reporting

Please report security problems privately: open a
[security advisory](https://github.com/DaniuPl/ThreadOS/security/advisories/new)
on GitHub rather than a public issue. Say what you did, what happened,
and what you expected; a disk image or a QEMU command line that shows
it is the best report there is. You will get an answer, and credit in
the fix if you want it.

## What the system trusts

- **Updates.** An installed system takes a new kernel, initrd and loader
  only when `update.txt` carries a valid ECDSA P-256 signature by the
  release key, and each file matches the SHA-256 that file lists
  (`user/update.c`). The public half of the key is built into the
  update program; the private half exists only as the `THREADOS_UPDATE_KEY`
  secret of this repository's release workflow. An admin can name
  another key in the file `update.key` on the system's disk.
- **TLS.** HTTPS connections check the server's chain against the
  roots built into `user/caroots.h` (generated by
  `scripts/mkcaroots.py`), plus `roots.der` on the disk if an admin put
  one there.
- **Users.** Changing the system - its settings, its system files,
  installing, updating - needs the admin password (`thread` until it is
  changed with `passwd`). Change it on any machine that matters.
- **Boot.** The UEFI loader is not signed for Secure Boot; it has to be
  turned off to start ThreadOS.
